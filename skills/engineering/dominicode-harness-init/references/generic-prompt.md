# harness-init · generic prompt

Part of the Contract Based Review Method (CBRM): Contract -> Lane -> Verdict.

For Codex, Cursor, Gemini CLI, or any agent with repository access.
Copy everything below the line and paste it into your agent, with the repo open.

---

Act as a verification engineer. You will set up this repository's harness: the mechanisms that automatically check whether code generated by an agent broke something.

Work in three phases and **do not move to the next one without showing me the result of the previous one**.

## Phase 1 · Audit (read-only)

1. Identify the stack from its manifests (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`, `*.csproj`, `Gemfile`, `composer.json`) and the package manager from the lockfile, not convention. If there are multiple manifests, this is a monorepo: ask which package we are working on.

2. Find candidate commands in the manifest scripts, `Makefile` / `Justfile` / `Taskfile`, and especially `.github/workflows` — CI usually reveals the project's real commands:
   build, type check, tests, lint/format, CI, e2e/smoke.

3. **Run every candidate.** Record the exact command, exit code, duration, and the last lines if it fails. Do not write any command later that you did not run here: a harness with invented commands is worse than having no harness.

4. Check whether agent configuration already exists: `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`, `.github/copilot-instructions.md`. If it exists, do not overwrite it — read it and then propose the diff.

5. Return this table:

```
| Mechanism  | Command | Status (OK / FAILS / DOES NOT EXIST) | Time |
```

## Phase 2 · Generation

First show me the list of files you will create or modify and wait for my confirmation.

Generate using **only the commands verified in Phase 1**:

- `AGENTS.md`, in exactly three sections:
  - **Contract**: where each task's acceptance criteria live, and the definition of done (every criterion has evidence, both loops green with no new reds, nothing in the diff the contract did not request).
  - **Lane**: stack, verification commands separated into a short loop (under 60s, after every change) and a long loop (before the PR), pre-existing known reds, conventions read from existing code, and boundaries you must not touch without permission.
  - **Verdict**: the report every task ends with: status, alignment (Exact / Tangling / Missing / Missing and Tangling) and a criterion -> status -> evidence table.
- A spec template with acceptance criteria where **each criterion includes the command that proves it**.
- A PR template with Contract, Lane and Verdict sections.
- A minimal CI workflow, only if there is no CI and I ask for it.

Rules: do not install dependencies, do not write tests to get to green, and do not add anything I did not ask for.

## Phase 3 · Report

```
## Your harness status

**Current level: N of 4**

- Level 0 — No harness: nothing automatically detects what the agent breaks.
- Level 1 — It compiles: build or type check.
- Level 2 — It behaves: tests and lint.
- Level 3 — Automatic: the long loop runs on every PR.
- Level 4 — With a verdict: spec acceptance criteria and agent review.

### Gaps, by impact
1. [gap] — [what it currently lets through]

### My next move
[ONE concrete action, with the command or file]
```

Do not inflate the level. If it is Level 0, say Level 0 — the value is knowing where you really stand.
