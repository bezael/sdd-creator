# Plan: Contract Based Review Method (CBRM)

Status: done
Updated: 2026-09-23

## Goal

Name and document CBRM as the method this repo ships: agents take a GitHub Issue to a verified PR, and the AI's code is judged against a **contract** (the spec's acceptance criteria), inside a **lane** (scope + boundaries + harness commands), producing a **verdict** (per-criterion evidence). No one approves AI code because it "looks right". To do this, CBRM gets named inside `dominicode-sdd-creator` and `dominicode-harness-init` joins the repo as the skill that writes the three-part `AGENTS.md`.

## Vocabulary (fixed before any file changes)

| CBRM piece | Spanish | What it is | Where it lives |
|---|---|---|---|
| **Contract** | contrato | Acceptance criteria, each with the command that proves it | `spec.md` §3/§4/§6 + `tasks.md` Verify lines (SDD), or the light `spec.template.md` (small Issues) |
| **Lane** | carril | What the agent may touch and how it checks itself: stack, short/long loop commands, conventions, boundaries, known reds | `AGENTS.md` (generated by harness-init) |
| **Verdict** | veredicto | Per-criterion PASS/FAIL with evidence, alignment (`Exact`/`Tangling`/`Missing`/`Missing and Tangling`), out-of-scope changes | Code Review + Final Verify output, PR template |

The flow becomes `Issue → Contract → Lane → Verdict → PR`. harness-init's current `Contract -> Harness -> Verdict` is renamed to `Contract -> Lane -> Verdict`, with "the harness" being the verification commands *inside* the lane.

## Risks / decisions

- **Two spec formats.** harness-init ships a light `spec.template.md`, and SDD ships the 6-section `spec.md`. Decision: the light one is the contract for Issues that SDD explicitly skips (clear bug fixes, single-file changes). Anything non-trivial uses SDD. `cbrm.md` states this rule so the two never compete for the same Issue.
- **"Harness" vs "Lane".** Existing content (and possibly published posts or videos) uses "harness". I keep "Harness Engineering" as the discipline name and "harness" as the verification commands. "Lane" is the `AGENTS.md` section that contains the harness plus scope and boundaries. It's a rename of the frame, not a removal of the word.
- **Source of truth moves.** After step 1, the repo copy is canonical and `~/.claude/skills/dominicode-harness-init` becomes an install target. Syncing the local copy back is left to you (a `cp -r` after merge).
- **CBRM authorship.** Unlike SDD, CBRM is your own named method. Credits read "CBRM by Bezael Pérez · Dominicode" while SDD keeps "SDD adaptation by". Tell me if you'd rather frame it as an adaptation too.
- Alternative rejected: a standalone `dominicode-cbrm` skill. It would duplicate SDD's review/verify phases and create a third source of rules.
