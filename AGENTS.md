# AGENTS.md — bezael/sdd-creator

This repo is a Claude Code marketplace (`dominicode`) with two plugins of Dominicode skills: `dominicode-sdd-creator` (engineering) and `dominicode-marketing`. It is also a Pi package. SDD (Spec-Driven Development) is an industry methodology — this repo distributes the **Dominicode adaptation** by Bezael Pérez, not the methodology's invention. Keep that framing in all docs and credits ("SDD adaptation by", never "methodology by").

CBRM (Contract Based Review Method) is Bezael Pérez's own named method, so its credit reads "CBRM by Bezael Pérez · Dominicode". Do not rewrite it as an adaptation, and do not rewrite SDD credits to match it.

The repo follows its own method: this file has the three CBRM parts, **Contract**, **Lane** and **Verdict**.

## Contract

Work starts from a contract, never from a vague request. The contract is the list of acceptance criteria in the task's spec, and each criterion has the command that proves it.

- **Where the contract lives:**
  - Features: `specs/<slug>/spec.md` + `tasks.md`, using the `dominicode-sdd-creator` skill. `specs/INDEX.md` lists every spec and the shared decisions.
  - Small Issues (clear bug, single-file change): a copy of `.dominicode/spec.template.md` at `.dominicode/specs/<issue-number>-<slug>.md`. Never fill the template in place.
- **No contract, no code.** If the task has no acceptance criteria, write them and get them approved before touching code.
- **The contract is the only source of scope.** If implementing it requires a decision the contract does not make, stop and update the contract first.

A task is done when:

1. Every acceptance criterion has evidence: which command proves it and what its output was.
2. The short loop and the long loop of the Lane pass, with no new reds.
3. The diff contains nothing the contract did not request.

Point 3 is the one most often missed. Extra code is code without a contract.

## Lane

The lane is where the agent is allowed to work and the harness it uses to check itself. Leaving the lane requires explicit permission.

### Stack

- **Language:** Markdown (skills, templates, docs), plain JavaScript ESM (`scripts/`), TypeScript run by Node's type stripping (`extensions/`, `tests/`)
- **Package manager:** none — no dependencies, no lockfile. Do not add one.
- **Runtime / version:** Node 22.18+ (CI uses Node 22)

### Harness

These commands have been run and checked. If one fails, the work is not done.

#### Short loop — after every change

```bash
node scripts/check.mjs   # 3s
npm test                 # 1s
```

#### Long loop — before opening the PR

```bash
node scripts/check.mjs   # 3s
npm test                 # 1s
```

The long loop is the short loop: both are fast enough to run on every change. CI runs them on every PR. The behavior evals (see [Evals](#evals)) are not part of either loop because each run costs real tokens; run them by hand when the contract touches `dominicode-sdd-creator`.

#### Known reds

None. The entire harness is green as of 2026-10-21.

### Conventions

#### Language

- **English**: all documentation — engineering `SKILL.md`, `AGENTS.md`, templates, references, category READMEs, `CHANGELOG.md`, GitHub release notes, `README.md` (with `README.es.md` as the Spanish mirror).
- **Spanish**: the marketing skills' content (`skills/marketing/*/`: `SKILL.md`, references, templates), because they write Spanish copy in a specific voice; announcement copy (X/LinkedIn posts in `announcements/`, generated by the `release-announcer` skill); and the `plugin.json` descriptions.

#### Structure

```
skills/
└── <category>/
    ├── README.md                  ← category index
    └── <skill-name>/
        ├── SKILL.md               ← instructions for Claude Code
        ├── AGENTS.md              ← generated from SKILL.md for other agents (Codex, Cursor, Gemini…)
        ├── templates/             ← templates used by the skill
        └── references/            ← reference material
```

Each plugin lists its skills in its own `plugin.json`, and `.claude-plugin/marketplace.json` lists the plugins:

| Plugin | Root (marketplace `source`) | Manifest | Version source |
|--------|-----------------------------|----------|----------------|
| `dominicode-sdd-creator` | `./` | `.claude-plugin/plugin.json` (`skills/engineering/*`) | `CHANGELOG.md` releases |
| `dominicode-marketing` | `./skills/marketing` | `skills/marketing/.claude-plugin/plugin.json` | its own `plugin.json` |

The root `package.json` is the **Pi package** manifest: its `"pi"."skills"` array lists every skill of both plugins, one folder each (a category folder would make Pi load its `README.md` as a skill), and its `version` follows the root `plugin.json`. Its `"pi"."extensions"` array ships `extensions/dominicode-verified-done.ts`, the Pi extension that runs the lane's short loop when the agent stops; `tests/` covers it with `node --test` (`npm test`, no dependencies, Node 22.18+ strips the types).

The root plugin also ships Claude Code hooks: `hooks/hooks.json` runs `hooks/verified-done.mjs`, the Claude Code side of verified done. Both sides call `extensions/verified-done-core.mjs`, so a change to the check goes there, with tests in `tests/` for each side.

Two plugins can't share a root: a second marketplace entry on `./` conflicts with the root `plugin.json`. A category that ships as its own plugin gets its own `.claude-plugin/plugin.json` inside `skills/<category>/`.

#### Adding a new skill

1. Create `skills/<category>/<skill-name>/` with at least `SKILL.md`, then run `node scripts/build-agents.mjs` to generate its `AGENTS.md`.
2. Add it to the `skills` array of the plugin that ships it: `"./skills/engineering/<skill-name>"` in `.claude-plugin/plugin.json`, or `"./<skill-name>"` in `skills/marketing/.claude-plugin/plugin.json`.
3. Add it to `"pi"."skills"` in the root `package.json`: `"./skills/<category>/<skill-name>"`.
4. If it's a new category, also create `skills/<category>/README.md`.
5. Update the catalog in the root `README.md`.

`SKILL.md` is the only file to edit. Each skill's `AGENTS.md` is generated from it (same body, no frontmatter): after editing a `SKILL.md`, run `node scripts/build-agents.mjs` and commit both files.

#### What `check.mjs` enforces

It fails when:

- a skill listed in a `plugin.json` is missing, its frontmatter `name` doesn't match its folder, or a skill on disk isn't listed by any plugin
- a `marketplace.json` entry doesn't use its plugin's `plugin.json` name, sets its own `version`, or points to a folder without a `plugin.json`
- the root `plugin.json` `version` differs from the latest released `CHANGELOG.md` entry (bump both together when cutting a release)
- `package.json` `"pi"."skills"` doesn't list exactly the skills of the `plugin.json` files, its `version` differs from the root `plugin.json`, it lacks the `pi-package` keyword, or a `"pi"."extensions"` entry is missing or left out of `"files"`
- `hooks/hooks.json` lacks its top-level `"hooks"` key or runs a `${CLAUDE_PLUGIN_ROOT}/…` script that doesn't exist
- a `SKILL.md` frontmatter breaks the Agent Skills rules Pi enforces: an unquoted `description` containing `: ` or ` #` (invalid YAML, so Pi drops the skill), a `name` that isn't lowercase-and-hyphens or is over 64 characters, or a `description` over 1024 characters
- a skill's `AGENTS.md` differs from what `scripts/build-agents.mjs` generates from its `SKILL.md`
- a `references/` or `templates/` path, or a relative Markdown link, points to a file that doesn't exist
- a Markdown table row has more cells than its header (escape `|` inside cells as `\|`)
- a tracked file has CRLF line endings, an SDD credit says "methodology by", or a `dominicode-harness-init` template contains an emoji

#### Current categories

- `engineering` — software development skills
- `marketing` — sales emails, offers, landing audits and launches, in Spanish (plugin `dominicode-marketing`)

### Boundaries

What the agent must not touch without explicit permission:

- Files outside the change scope declared in the contract
- Dependencies: the repo has none; do not add any
- `.github/workflows/` and the release flow (version bumps, tags, `CHANGELOG.md` release headings)
- A skill's generated `AGENTS.md` by hand: edit its `SKILL.md` and regenerate
- Credits and the SDD/CBRM framing above
- Secrets, `.env` files, and credentials

## Verdict

The verdict is what the reviewer reads instead of the diff. The agent does not say "done"; it delivers a verdict, and the verdict is only as good as its evidence.

Report it in the PR (or the hand-off) in this format:

```markdown
Status: PASS | CHANGES REQUIRED
Alignment: Exact | Tangling | Missing | Missing and Tangling

| # | Acceptance criterion | Status | Evidence |
|---|----------------------|--------|----------|
| 1 | ...                  | PASS   | `command` -> output |

Long loop: {{summarized output}}
New reds: none | {{list}}
Out-of-scope changes: none | {{list with justification}}
Not run: none | {{checks that were not executed, and why}}
```

- **Exact**: the change covers every criterion and nothing else. **Tangling**: it includes code no criterion asks for. **Missing**: a criterion is not satisfied. **Missing and Tangling**: both.
- Only `Exact` can be `PASS`, unless the deviation was accepted and written into the contract first.
- A check that was not executed is reported as *not run*, never as PASS. Behavior evals not run on a change to `dominicode-sdd-creator` go here.
- The reviewer inspects the diff only where the verdict is red or the evidence is missing.

## Evals

`evals/` holds behavior evals for `dominicode-sdd-creator`, run with `claude plugin eval`. They check the hard rules a prompt edit can silently break:

| Case | Asserts |
|------|---------|
| `no-tdd-not-inferred` | "hazlo rápido, es un prototipo" with no runner → proposes a runner, never offers skipping tests, writes no `tasks.md` yet |
| `explicit-no-tests` | "No quiero tests" → asks "not now vs never" and for confirmation before any task list |
| `low-context-intent-first` | "Quiero hacer una app de recetas" → skill fires, interviews the idea, writes no `spec.md` |
| `high-context-triggers` | Detailed feature in a Fastify/SQLite/Vitest repo → skill fires, writes `spec.md` only, no new stack, stops for confirmation |
| `bugfix-no-trigger` | Failing test with a clear repro → skill does not fire, bug fixed directly |

Run them after any change to `SKILL.md`, its templates or its references, and before a release:

```bash
claude plugin eval . --ablation none --scaffold --allow-tools Write Edit --trust-plugin --no-publish -j 5
```

- About $3 and 2 minutes for the full suite (5 cases × 3 runs). Use `--case <name> --runs 1` while iterating.
- `--scaffold` runs each case's `scaffold.sh` to create its fixture repo; only use it on cases from this repo.
- `--ablation none` skips the no-plugin baseline arm, which would double the cost and leave the `Skill` graders unscored.
- Results go to `evals/results/` (gitignored). Add `--keep-temp` to inspect a run's workspace and `trace.jsonl`.
- `Write`/`Edit` graders match the tool's JSON input. Anchor them on `"file_path"`, or a file's content will match too.
- They are not in CI: each run spends real model tokens on your account.
